# llama-android-vulkan-build

Cross-compiled **llama.cpp (b11913)** for **Android arm64** with a **working Vulkan (GPU)**
backend, targeting **Mali-G77** (MediaTek Dimensity 1200-AI / MT6893, OnePlus Nord 2 5G).

Built entirely in **GitHub Actions** (Android NDK r27c). No local Linux/NDK needed.

> Status: **GPU inference works.** `llama-bench -ngl 99` runs to completion with no segfault
> and gives up to **~9x faster token generation** over the CPU backend on the test model.

---

## Why this exists

llama.cpp's Vulkan backend detects the Mali-G77 and plans all layers on it, but the
`ggml-vulkan` binary **segfaults during setup** on this class of device.

The Android Vulkan loader (`/system/lib64/libvulkan.so`) is **spec-correct**, whereas desktop
loaders are lenient. Combined with the Mali driver advertising Vulkan 1.2 features whose
entry points it does **not** actually expose, this produces a chain of NULL function-pointer
calls (`pc = 0`). Each fix moves the crash further along until inference succeeds.

This is related to upstream llama.cpp **PR #28593** ("vulkan: fix three null-pointer crashes on
pre-1.2 devices reporting VK 1.2 features") and issue **#30920** (Mali still crashes in
`QueueSubmit` after applying that PR). This repo applies the PR-28593 logic **plus a fix for the
remaining `QueueSubmit` crash**, which to our knowledge is not fixed upstream yet.

---

## The crash chain and the fixes

All patches live in `.github/workflows/build.yml` (applied to a fresh llama.cpp checkout at
build time). There are five of them:

| # | Root cause | Fix |
|---|-----------|-----|
| 1 | `VULKAN_HPP_DEFAULT_DISPATCHER` was only `init()`'d against the `VkInstance`. Spec-correct loaders return `NULL` for device-level functions from `vkGetInstanceProcAddr`. | Re-`init()` the dispatcher with the `VkDevice` after `createDevice()` (as the Vulkan-Hpp docs recommend). |
| 2 | `device->buffer_device_address` is taken straight from the Vulkan-1.2 feature bit, but the backing `VK_KHR_buffer_device_address` extension is not enabled on a pre-1.2 driver → `vkGetBufferDeviceAddress` is `NULL`. | Enable `VK_KHR_buffer_device_address` when `apiVersion < 1.2`. |
| 3 | Same gap for `VK_KHR_timeline_semaphore`, used unconditionally by the backend's own synchronization. | Enable `VK_KHR_timeline_semaphore` when `apiVersion < 1.2`. |
| 4 | `VK_KHR_16bit_storage` is requested unconditionally, but it is core since 1.1 and some drivers stop listing it → `VK_ERROR_EXTENSION_NOT_PRESENT`. | Only request it when `apiVersion < 1.1`. |
| 5 | **Mali-specific:** the driver reports `VK_KHR_internally_synchronized_queues` / returns a **NULL `VkQueue`** from `getQueue2()`. `vkQueueSubmit(NULL, ...)` then crashes inside the loader. | Disable internally-synchronized queues on Mali, and fall back to `getQueue()` (Vulkan 1.0) if `getQueue2()` yields a NULL handle. |

Items 1-4 are exactly the PR-28593 fixes. Item 5 is the extra bit needed to get past the
`QueueSubmit` crash described in issue #30920.

## Results

Test model `Qwen2 1B Q4_K_M`, `llama-bench`, Android arm64 (bionic), Mali-G77 MC9:

| backend | test | t/s |
|---------|------|-----|
| Vulkan (ngl 99) | pp128 | **36.9** |
| CPU (ngl 0)     | pp128 | 27.2 |
| Vulkan (ngl 99) | tg32  | **13.4** |
| CPU (ngl 0)     | tg32  | 1.49 |

-> token generation ~**9x** faster on GPU; prefill ~1.4x. No segfault.

On `Qwen3.5-4B Q6_K` (3.85 GiB): pp64 6.7 t/s, tg16 2.5 t/s, `-ngl 99`, clean exit.

Note: Mali-G77 has no matrix cores and no integer-dot support, so gains are real but not
dramatic; a Snapdragon/Adreno device would go much faster.

## How to build

1. Fork/push this repo.
2. **Actions -> `build-android-vulkan` -> Run workflow**.
3. Wait ~10-15 min.
4. Download the `llama-android-arm64-vulkan` artifact (`.tar.gz` with `llama-cli`,
   `llama-server`, `llama-bench`, `lib*.so`).

## How to run on the device

```bash
adb push llama-android-arm64-vulkan.tar.gz /data/local/tmp/
adb shell 'mkdir -p /data/local/tmp/llama-gpu && cd /data/local/tmp/llama-gpu && tar xzf /data/local/tmp/llama-android-arm64-vulkan.tar.gz'
# the binaries use the Android Vulkan loader + the vendor Mali ICD automatically
adb shell 'cd /data/local/tmp/llama-gpu && LD_LIBRARY_PATH=. ./llama-bench -m model.gguf -ngl 99 -p 128 -n 32'
```

`LD_LIBRARY_PATH=.` is required (Android does not search the binary's directory by default).

## Build configuration

- Android NDK r27c, arm64-v8a, `android-28`, Clang
- `GGML_VULKAN=ON`, `GGML_BACKEND_DL=ON`, `GGML_NATIVE=OFF`,
  `GGML_CPU_ARM_ARCH=armv8.2-a+dotprod`, `GGML_OPENMP=OFF`, `LLAMA_CURL=OFF`, `LLAMA_OPENSSL=OFF`
- Vulkan shaders are generated by a **host** `vulkan-shaders-gen` (`glslc` + host gcc); the
  NDK does not ship `vulkan/vulkan.hpp` or `spirv/unified1/spirv.hpp`, so Khronos
  Vulkan-Headers + SPIRV-Headers are fetched and put on the include path.
- A wrapper toolchain (`cmake/android-vulkan-toolchain.cmake`) sets
  `CMAKE_FIND_ROOT_PATH_MODE_PACKAGE=BOTH` so the host `SPIRV-Headers` CMake package is found
  while libraries/headers still come from the NDK sysroot.
